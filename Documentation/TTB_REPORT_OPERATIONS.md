# TTB report ingestion and reconciliation

Source: bank PDF page23/24 (Cross-border301) and attached2.38 Excel (legacy). The Excel's reserved area differs from the later PDF. Neither is auto-detected from plausible data. All bundled test inputs are synthetic; no bank-produced encrypted file or approved SFTP profile is available yet.

## Provisioning and boundaries

`Reports.Enabled` defaultsfalse. An approved environment profile must explicitly select `Layout` (`CrossBorder301`/`Legacy238`), `Width` (`Utf8Bytes`/`UnicodeScalars`), `CreditTotal` (`IncludesVoidedOriginals`/`ExcludesVoidedOriginals`), `DailyScope` (`CalendarDay`/`BankingDay2256`), sequence/trailer convention, filename/header-date agreement and company receiving account. UTF8 decoding is strict; UnicodeScalars counts codepoints, not grapheme clusters. Actual Thai bank files must establish the correct convention. A third convention requires an explicit new parser version.

The SFTP host is derived exclusively from the deployment environment's TTB gateway; directory is fixed `/QRTRAN/report/`. Only an exact `BPQR_ISO_YYMMDD.TXT` or `BPQRLOST_YYMMDD.TXT` logical name is accepted, with an explicitly provisioned remote suffix (``, `.pgp`, `.gpg`, `.asc`). Port4028 is the default;4022 is permitted only when the approved bank profile selects it. Encryption is mandatory on either port. File length/write time must remain stable across the download; symlinks/directories and oversized files are rejected.

Set `HostKeySha256` to the fingerprint confirmed through the bank's key exchange, not a value learned by blindly accepting the first connection. SSH.NET compares the SHA256 of the received host-key blob using a constant-time comparison. There is no ignore-host-key or alternate-host switch. The current adapter uses provisioned username/password; a different bank authentication contract needs an explicit adapter.

PGP uses the environment's private secret-key file/passphrase and exact encryption-key fingerprint. AES256 and integrity protection are mandatory. Compressed and uncompressed packet streams and final plaintext have independent size bounds. An encrypted filename never chooses a local path. If the bank signs files, provision its signing public-key file and exact signing-key fingerprint; binary-document signatures with SHA256/384/512 are verified. A required but absent, invalid or unexpected signature quarantines the file. Keys/passphrases/raw payer information never enter logs or public configuration.

`ttb-reports` credentials and `ttb-report-keys` files mount only in the commerce worker, not the API, WebGL, browser or receipt worker. The private storage PVC holds the encrypted originals; the database stores private normalized evidence. Production checkout also requires `Reports.AcceptanceApproved=true`, set only after successful bank/file acceptance and operational review. API processes do not need the SFTP password or PGP private key. Acceptance metadata is not proof of an active bank connection; worker/file monitoring remains required.

## Durable processing

1. Download a complete bounded encrypted file. Create a report record with environment, merchant, logical filename, date, immutable cipher SHA256/size and sequential revision under a filename lock. Store it atomically under its content hash before committing the record and `report.stage` job.
2. Re-read and verify encrypted bytes, decrypt in memory, hash plaintext, validate the complete file, merchant, Biller and receiving account. Validate500 positions, H/D/T order, sequence, real Gregorian date/time, numeric implied-two-decimal amounts/fees, fields and trailer totals before staging any rows. Bad files become `Quarantined` with a safe validation code and a finance case; encrypted originals remain.
3. Stage immutable typed rows with semantic hashes and one durable `report.row` job each. A repeated ciphertext returns its original report. Re-encryption with identical plaintext becomes `Replay` of the first staged report. Changed plaintext under the same filename becomes `RevisionReview`, with no new rows/effects until an authorized finance reprocess records its reason/profile.
4. Reconcile under the same bank-instruction lock as callback/Verify, followed by order locks. Per-row application and its audit/case commit together. Replaying a row does not apply it again. Completion counts are serialized, so concurrent final rows cannot leave a file permanentlyStaged.

The original parser profile is recorded at archive time, and the successful applied profile is recorded separately. A reprocess appends its reason, previous/new profile and staging result to the audit trail; it never deletes old evidence or overwrites staged rows. Stage failures complete as a quarantined outcome rather than blindly retrying malformed financial data. Transport failures have bounded retries and safe error codes.

## Planned PGP rotation and retained archives

New archives also snapshot a `crypto` object containing the exact configured recipient and signing fingerprints. No private key, passphrase or key path is stored in that object. Staging verifies the immutable ciphertext hash before using the snapshot. A parser/account repair keeps the original crypto snapshot; its applied profile and audit record identify the keys actually selected. Complete/Staged/Replay rows remain immutable and cannot be reprocessed just to test a rotation. No public plaintext-view/download endpoint is introduced.

`RecipientFingerprint` and `SigningFingerprint` select the current encryption and bank signing keys. Optional `ArchiveRecipientFingerprints` and `ArchiveSigningFingerprints` permit planned retired keys only when the same exact pin was recorded on an existing archive. Both lists default empty, allow at most eight distinct full40/64hex fingerprints each, and reject wildcards, duplicates and the active pin. Keeping an old key in the keyring is insufficient permission. A newly imported file snapshots the current pins and cannot use these lists to accept a retired recipient or signer. Removing a retired pin blocks further decryption with it. These lists are not a way to trust a revoked/compromised key.

The current private/public key paths point to complete provisioned OpenPGP keyrings containing the approved active and retained keys. The worker uses one configured passphrase for the selected secret key: retained secret keys must be securely packaged with that passphrase, or a different explicitly designed key adapter is required. Preserve historical private material under the company's separate recovery/custody policy; ciphertext backups alone cannot recreate lost PGP keys. The backup CMS recipient and bank JWT/TLS/SFTP keys have separate lifecycles.

For a planned rotation:

1. Confirm the exact encryption and bank signing fingerprints through the bank's approved exchange. Verify the intended environment and effective switch time; never learn trust from a received file alone. Drain/archive the expected old-key report backlog before switching. A first-seen old-key file after the switch is quarantined: request a bank re-encryption with current keys or a separately reviewed per-file recovery procedure; do not broaden new-file trust using the archive lists.
2. Securely retain the old complete keyrings and prepare the combined old/new rings. Add the old pins to the archive-only lists while selecting the new active pins in the worker's environment-specific configuration. With Kubernetes Secret environment variables, use `Reports__ArchiveRecipientFingerprints__0` / `Reports__ArchiveSigningFingerprints__0` for the first retained pin. Restart only the owned worker after the Secret/keyring update; do not assume environment variables reload on Secret projection.
3. On isolated synthetic fixtures, verify new/new succeeds, new files using old recipient or old signer fail, an existing old/old archive succeeds only with both archive permissions, corruption still fails, and replay/reconciliation cannot duplicate allocations or delivery. Test the actual bank's new sample/profile in UAT before acceptance.
4. Review archive/quarantine/overdue cases and audit evidence during the agreed switch. Do not delete old decryption material until all retained reports/backups and the approved retention policy permit it. Remove compromised pins and close the affected transport; investigate quarantined originals instead of weakening integrity/signature requirements.

An archive produced before crypto snapshots existed uses **current pins only**. It never guesses a retired key from its filename or keyring. An unsigned archive cannot bypass a newly required signing policy. Legacy/incorrect crypto metadata and unsigned-to-signed transitions therefore require an explicit reviewed evidence-migration procedure; the normal finance reprocess does not rewrite original crypto identity. There are currently no real bank archives in UAT, so no historical bank metadata migration has been performed or claimed.

Once archive key rotation is in use, a rollback/resumed worker must retain capability `pgp-archive-key-rotation-v1` as well as the financial reader floor and approved keyrings/trust configuration. Reader contract3 alone does not establish this capability. An older worker that can only use current keys is not an archive recovery procedure; use a compatible forward release and preserve quarantine/audit evidence.

## C, D, V and LOST

- `C` is credit evidence. An exact existing bank instruction must match QRId, references, amount and cross-border metadata before an ISO row can enrich the original credited-payment timestamp. LOST payer debit and operation CreditAt stay separate in immutable row evidence; neither is relabeled as the original credit time or replaced by callback system time. No FX conversion or fee deduction from the order amount is inferred.
- `D` is the void debit linked by its exact OriginalInstructionId. `V` marks the original credit as voided. Both set the same original payment's `Voided` flag. V never creates a second debit, and neither deletes the original allocation or receipt. Digital rights are revoked and pending physical delivery is held; shipped/delivered history and stock are preserved for finance review. The separate Void slip belongs toP7-02.
- Report InstructionId fields are35 columns; API identifiers may be50. Prefix detection can open a width-mismatch case but never establishes identity. Unknown/unallocated report credits, amount/reference/time conflicts and unknown voids open finance cases and hold a matching order. The report pipeline does not guess a full API identifier, silently create another payment, reserve already-released stock or automatically deliver a late order. Authorized finance recovery is handled throughP7-03 with explicit evidence and stock checks.
- Trailer convention for V is explicitly provisioned. Debit totals count onlyD; credit totals include or excludeV according to the approved convention. V totals are also recorded separately. Full-file totals alone do not prove settlement or matching all local payments; end-of-day comparison and case review remain finance responsibilities.

After all rows commit, `report.compare` performs the reverse ISO comparison against ledger payments with known original bank timestamps within the applied approved day scope. CalendarDay is Bangkok00:00–24:00; BankingDay2256 is previous22:56 to report-date22:56. A known payment missing its exact original ID from C/V rows opens `LocalPaymentAbsentFromReport`; it does not erase payment or delivered history. The summary records known gross, bank credit/debit totals and the count of ledger entries whose original time remains unknown. It never substitutes callback/Verify system time to claim a complete daily match. LOST is explicitly marked repair-rows-only and cannot prove daily absence. These facts support finance review; they are not a claim that the bank statement has settled.

## Schedule and operations

Worker checks datesD-1 through the configured bounded lookback (default7days), throttled per persisted file to30minutes. ISO deadline defaultsD+1 at01:00Bangkok, after the documentedD0 23:45 publication. LOST deadline defaultsD+1 at20:00, after the tentative13:00–19:00 window. These are proposed operational deadlines pending bank agreement, not claims that the bank guarantees them. Missing files remain `WaitingForFile`; they never mean zero transactions. A past-deadline file opens one `ReportOverdue` case. A later download resolves that timeliness case with its archive ID; validation/money exceptions have separate cases. The worker continues checking recent files to detect revisions.

`GET /admin/reports` and `GET /admin/reports/{id}` require finance/admin and no-store. Summary responses exclude payer rows and private filesystem paths. `POST /admin/reports/{id}/reprocess` also requires Origin/CSRF and a reason. It is an audited approval of an unstaged revision/repair; already staged rows remain immutable. There is no public plaintext-upload or report-download route.

When provisioning arrives: verify host/key fingerprints out of band, select the actual file/layout/encoding/date/totals profile, mount worker-only credentials, run real ISO/LOST/Thai/C-D-V/cross-border fixtures in UAT, check replay/reissue and missed-file recovery, compare totals with bank settlement, and record acceptance before enabling Production. Do not put passwords or private keys in this document, git or chat.
