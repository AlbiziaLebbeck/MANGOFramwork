# P7-02 Void contract and implementation constraints

Reviewed from the supplied PDF pages10–16 and13's sample slip. This is the implementation contract for the next task, not evidence that Void is implemented or bank-approved.

- Outgoing adapters already route MerchantVoid and EnquiryVoid through pinned bank HTTPS/JWT. Body: TransactionId17=`Merchant3+yyyyMMddHHmmss`, original full InstructionId, QRId20, Biller15, current TransDate. The response table's15-character TransactionId conflicts with its17-character request/example; enforce the17-character echoed request pending UAT.
- Full void only; no amount field and no partial refund endpoint. CrossBorderFlagY and original InstructionId startingQ are ineligible. Daily cutoff is22:56Bangkok. The diagram groups by banking window while prose says same day; use an explicit approved window policy, defaultUnknown/disabled. Never extend eligibility from a fresh callback/Verify system timestamp. A proved ISO original payment time or a complete issuance→first trusted credit bound wholly inside the approved window is required. LOST debit/repair timestamps must not be relabeled as original credit time.
- Require finance/admin, Origin/CSRF, reason and stable operation ID. Lock original bank instruction→order→void operation. Persist the intent, immutable original identifiers and delivery/game hold before any network call. Allocate TransactionId under a merchant/second uniqueness guard; do not invent subsecond digits or reuse a timestamp ID.
- A durable send fence must commit before the bank POST. Once fenced, job retries must never blindly send MerchantVoid again: a crash could occur before or after the bank receives the request. Preserve Unknown and use EnquiryVoid with the original TransactionId. All raw responses, request correlation, parse/transport outcomes and audit remain private evidence.
- Strict response matching: HTTP200, flat JSON without duplicate keys, exact TransactionId/InstructionId/QRId/Biller, valid ResCode/ResDesc/system TransDate. Merchant0000 confirms;0002 means original already voided and needs accurate observation wording.0003/0004/0008/0009 are explicit rejections/reviews.0001 duplicate ID,0005 internal error,9999, timeouts, malformed/mismatched/unknown responses remain uncertain and require enquiry. Do not infer success from description text. Enquiry0000 confirms voided;0003/notfound/error is not proof that resending is safe.
- Enquiry must be bounded, correlated and rate-limited, using a persisted request count/lease before network. One recovery read after a requested void can be bounded; there must be no indefinite bank polling. Explicit operator checks cannot create a second void operation while the first remains uncertain.
- Reuse one reducer for reportD/V and direct/enquiry confirmations: originalBank.Voided=true, paymentVoided, retain original allocation/receipt, revoke digital rights, hold pending physical delivery and preserve shipped/delivered/stock history. No automatic restock, partial refund or fabricated reversal of a downloaded file. The business review/acknowledgment policy for already shipped/downloaded goods remains explicit and defaultclosed.
- Queue a separate immutable Void slip after confirmed void. One number/snapshot per order/document kind, preserve the original receipt, retry the same PDF bytes/number. State whether timestamps mean observed confirmation or actual bank event; bank TransDate is system time. Include original payment/order/reference, full void amount, reason/operator evidence and issuer, without pretending the company document is a bank slip or tax invoice.
- Extending ReceiptSnapshot must preserve old canonical hashes: an optional Void metadata property must be omitted when null (JsonIgnore.WhenWritingNull), or use a separate typed document version/renderer. Never deserialize an old receipt then serialize a new null field into its hash. Verify both old receipts and real Thai Void PDF visually on Windows/Linux.

Acceptance needs concurrency/idempotency, cutoff boundaries, missing original time, fulfilled/digital policy, transport/crash unknown→enquiry, all response codes and mismatched echoes, original receipt preservation, role/CSRF/ownership and actual Thai PDF evidence. Real bank acceptance and company refund policy remain external gates, separate from Local/mock tests.
