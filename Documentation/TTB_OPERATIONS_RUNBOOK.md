## Restore and freeze

1. Confirm an encrypted backup and its independently recorded transfer hash, recipient/key custody, environment and reader contract. A same-VM copy alone does not cover VM loss. CurrentUAT DPAPI recovery works only for the designated Windows account; production escrow is still unapproved.
2. Restore into a newly named isolated namespace/database/private directory first. Do not overwrite current UAT or Production. Deny egress and start no commerce/PDF/report worker or bank connection. The original source and encrypted archive remain untouched.
3. Run`decrypt-backup.ps1` into a fresh restricted directory, then`verify-backup-bundle.py` with the expected environment and recipient fingerprint. It rejects paths/links/unsupported file types, wrong environment/reader and content-hash mismatches. Its`databaseRestored:false` result is deliberate: structural verification is not a SQL restore.
4. Restore the PostgreSQL custom archive using the matching supported PG client into the fresh target, with error-on-failure and a single transaction. Verify all constraints, immutable money/stock/job/numbering data and every database-referenced private file hash. Preserve operation UUIDs, allocations, send fences and unknown Void states.
5. Before any live recovery, scale all financial writers to zero. Use a release with reader contract≥3 and `operations-freeze-v1`, set`Operations__RecoveryFreeze=true` on every new API/worker process and verify health`recoveryFrozen:true`, paymentsReady:false, and no job leases/mutations. Setting an unknown flag on the old contract2 binary does not freeze it.
6. During freeze all mutation methods, including callbacks, return503; this is read-only inspection, not callback ingestion. Reconcile the loss interval using trusted bank evidence/reports before resuming. Bank retries may expire during a long outage, so missing callbacks must be reconciled rather than assumed delivered.
7. Resume only after the authorized operations/finance owners confirm the reconciled state, company policy and target environment. Restart compatible roles with freeze cleared in a controlled order and observe original queued effects. Do not replay a bank command solely because its old job is pending after restore.

## Safe release and rollback

- Use immutable release directories and verify the archive SHA256 before migration/rollout. Preserve the separate runtime SQL role and exact environment marker. No shared KKU controller/route/database change is part of a TTB release.
- The deployment tool enforces `/opt/ttb-commerce/uat/minimum-reader-contract`. Contract2 adds Refunded/manual/goods; contract3 adds recovery freeze. Every API/worker must meet the floor. Do not use raw rollout-undo to an older binary which ignores persisted state or the freeze flag.
- Financial/evidence/return Down migrations refuse to discard populated records. Prefer a compatible forward fix. Taking an older backup is a recovery incident and requires the freeze/reconciliation procedure, not a routine code rollback.
- Validate readiness, payments/reports flags, private ingress state, worker behavior and KKU readiness after deployment. A green pod alone is not a payment acceptance test.
