# ระบบชำระเงิน MANGOs x TTB
## คู่มือทำความเข้าใจระบบและคอนโซลทดสอบ UAT

สำหรับคุณสิรภพ แสงทองคำ | วันที่ 21 ตุลาคม 2569

**ผู้รับเงิน: บริษัท สร้างสรรค์ปัญญา จำกัด**

รายงานนี้อธิบายระบบที่เว็บไซต์ `plus.mangosgo.com/ttb-uat/` ใช้งานอยู่ และส่วนทดสอบที่เพิ่มสำหรับธนาคาร ใช้ภาษาแบบผู้เริ่มต้น โดยมีคำสั่งสำหรับตรวจระบบด้วยตัวเองอยู่ท้ายคู่มือ

### อ่านหน้านี้ก่อน

ระบบมีงานสองประเภท งานแรกคือการซื้อสินค้าของผู้ใช้ใน UAT ซึ่งต้องตรวจเงินก่อนส่งสินค้า งานที่สองคือการทดสอบ API กับธนาคารโดยใช้ **Ref1=TEST** ซึ่งเก็บประวัติในคอนโซลแยกและไม่สร้างออเดอร์ ใบเสร็จ หรือสิทธิ์สินค้าให้ผู้ใช้

ชื่อผู้รับเงินในแอปของเราเปลี่ยนผ่าน backend เป็นชื่อบริษัทตามภาพที่ยืนยันแล้ว ส่วนชื่อในแอปธนาคารมาจากข้อมูล Biller ที่ธนาคารลงทะเบียน การตั้งค่าในระบบของเราไม่สามารถแก้ทะเบียนชื่อผู้รับเงินของธนาคารได้

### สิ่งที่เปลี่ยนในรอบนี้

- เปลี่ยนชื่อผู้รับเงินจากชื่อชั่วคราวเป็นชื่อบริษัท
- เพิ่มคอนโซล UAT สำหรับสร้าง QR ที่ Ref1=TEST และติดตาม Notification, Verify, Void และ Enquiry Void
- เพิ่มประวัติถาวรในฐานข้อมูล พร้อมผลตอบกลับ Request UID และเวลาของแต่ละเหตุการณ์
- เพิ่มทางดู log ผ่าน SSH และสคริปต์ตรวจออเดอร์แบบอ่านอย่างเดียว
- ยืนยันการรับ callback ของ UAT จากหลักฐานธนาคารจริงที่มีอยู่แล้ว จึงปิดโหมดเปิด checkout เพื่อรอ callback ครั้งแรก

**ขอบเขต:** การเปลี่ยนแปลงนี้ใช้กับ UAT เท่านั้น การใช้ธนาคารจริงใน Production ยังต้องตรวจรับและตั้งค่าของ Production แยกต่างหาก

## 1. Payment ทำงานอย่างไร

สมมติผู้ใช้ซื้อดาวดิจิทัลราคา 1 บาท เว็บไซต์ต้องรู้ว่า “เงิน 1 บาทนี้เป็นของคำสั่งซื้อไหน” และต้องไม่ส่งดาวซ้ำถ้าธนาคารแจ้งรายการเดิมกลับมาหลายครั้ง นี่คือหน้าที่หลักของระบบ Payment

| คำที่เห็น | ความหมายแบบเข้าใจง่าย |
|---|---|
| QR Code | ภาพที่บรรจุข้อมูลผู้รับเงิน ยอดเงิน และเลขอ้างอิงสำหรับให้แอปธนาคารอ่าน |
| Biller ID / BillerNo | รหัสผู้รับชำระเงินที่ธนาคารลงทะเบียนให้บริษัท: 075555900002101 |
| Merchant ID | รหัสเชื่อมต่อ API ของบริษัท: PYA |
| Ref1 | เลขอ้างอิงหลัก ออเดอร์ซื้อสินค้าใช้เลข เช่น T20261021000002; งานทดสอบใช้ TEST |
| Ref2 | เลขอ้างอิงเพิ่มเติม ช่วยจับคู่ให้ตรงรายการ; คอนโซลสร้างค่า BT... ใหม่ให้แต่ละชุด |
| QRId | รหัสเฉพาะของ QR แต่ละใบ แม้ Ref1=TEST เหมือนกัน QRId ก็ไม่ซ้ำกัน |
| InstructionId | รหัสรายการเงินที่ธนาคารแจ้งมา ใช้ตรวจซ้ำและอ้างอิงเมื่อ Void |
| API | ช่องทางที่โปรแกรมสองฝั่งส่งคำขอและคำตอบให้กัน |
| Backend | โปรแกรมบน server ที่ตรวจข้อมูล เก็บรายการ และติดต่อธนาคาร |
| UAT | วงทดสอบร่วมกับธนาคาร ต้องใช้ช่องทางหรือบัญชีทดสอบที่ธนาคารจัดให้ |

### มีคำถามถึงธนาคาร 3 แบบที่ควรแยกกัน

**Notification หรือ noti:** ธนาคารเป็นฝ่ายโทรมาบอกระบบเราว่ามีรายการเงินเข้า

**Verify:** ระบบเราเป็นฝ่ายถามธนาคารว่า QR นี้มีผลชำระเงินหรือยัง ใช้ช่วยยืนยันเมื่อ callback ยังมาไม่ถึงหรือกำลังตรวจปัญหา

**Void และ Enquiry Void:** Void คือคำขอยกเลิกรายการที่ธนาคารรองรับ ส่วน Enquiry Void คือถามว่าคำขอ Void เดิมสำเร็จหรือยัง การถามผลไม่ได้ส่งคำขอยกเลิกใหม่

**จำง่าย:** ภาพสลิปหรือ HTTP200 เพียงอย่างเดียวยังใช้ตัดสินว่าออเดอร์ชำระสำเร็จไม่ได้ ต้องตรวจรหัสผลธุรกิจ เลขอ้างอิง ผู้รับ และยอดเงินให้ตรงกันด้วย

<div class="flow"><b>Unity / เว็บไซต์</b><span>เลือกสินค้าและยืนยันยอด</span><i>↓</i><b>Backend ของ MANGOs</b><span>สร้างออเดอร์ จองสินค้า และสร้าง QR</span><i>↓</i><b>แอปธนาคารในวง UAT</b><span>สแกนและชำระตาม QR</span><i>↓</i><b>TTB แจ้ง Credit Notification</b><span>Backend ตรวจแหล่งที่มา รหัสอ้างอิง และยอด</span><i>↓</i><b>ฐานข้อมูล → งานส่งสินค้า / ใบเสร็จ</b><span>บันทึก Paid ก่อน แล้วทำงานต่อแบบตรวจซ้ำได้</span></div>

1. ผู้ใช้เข้าสู่ระบบ MANGOs และเลือกสินค้า Backend เป็นผู้คำนวณยอดจริง จึงไม่เชื่อยอดที่หน้าเว็บส่งมาอย่างเดียว
2. เมื่อยืนยัน ระบบสร้างออเดอร์และจองสินค้าตามเงื่อนไข จากนั้นสร้างข้อมูล QR ตามรูปแบบ TTB แล้วแปลงเป็นภาพบนหน้าเว็บ ไม่ต้องเรียก API ของธนาคารเพื่อสร้างภาพ QR ทุกครั้ง

4. ตรวจว่า BillerNo, QRId, Ref1, Ref2 และจำนวนเงินสัมพันธ์กับออเดอร์ ถ้าตรงจึงบันทึกเงินเข้าและจัดสรรยอดให้ออเดอร์
5. ระบบบันทึกผลถาวรก่อนตอบ ACK กลับธนาคาร ถ้า noti เดิมมาอีกจะเก็บการส่งซ้ำและตอบรหัสรายการซ้ำ แทนการให้สินค้าหรือเพิ่มเงินซ้ำ
6. Worker ทำงานส่งสินค้า เปิดสิทธิ์ดิจิทัล และสร้างใบเสร็จจากงานที่บันทึกไว้ หน้าเว็บอ่านสถานะล่าสุดจาก backend

### องค์ประกอบบน ntserver02

- **API:** รับคำขอจากเว็บ รับ noti และให้บริการคอนโซลทดสอบ
- **PostgreSQL:** เก็บออเดอร์ หลักฐานธนาคาร ประวัติ และสถานะถาวร
- **Commerce worker:** ทำงานเบื้องหลังเกี่ยวกับออเดอร์และส่งสินค้า
- **Receipt worker:** สร้างไฟล์ใบเสร็จและจัดการงานเอกสาร

## 3. ทำไมต้องมี key และตรวจ callback

### ตอนระบบเราติดต่อ TTB

Backend สร้าง JWT ซึ่งเป็นข้อความยืนยันตัวตนระยะสั้น และเซ็นด้วย RSA private key ของเรา ค่า issuer ที่ใช้คือ `jwt-key-pya` และใช้ลายเซ็นแบบ RS256 ธนาคารใช้ public key ที่ลงทะเบียนไว้ตรวจว่าลายเซ็นถูกต้อง

**Private key** เปรียบเหมือนตราประทับของบริษัท ต้องอยู่ฝั่ง server เท่านั้น ส่วน **public key** เป็นข้อมูลที่ให้ธนาคารใช้ตรวจตราประทับได้ ไม่ใช่รหัสผ่านและใช้เซ็นแทนเราไม่ได้ UAT กับ Production ใช้คนละคู่ key

Certificate ของ HTTPS เป็นอีกเรื่องหนึ่ง ใช้ตรวจตัวตน server และเข้ารหัสการรับส่งข้อมูล จึงต้องติดตามวันหมดอายุและการเปลี่ยน cert ตามที่ธนาคารแจ้ง ไม่ควรปิดการตรวจ certificate เพื่อให้เชื่อมต่อผ่าน

### ตอน TTB ติดต่อกลับมาหาเรา

TTB ยืนยันว่าตัวส่ง Credit Notification ชุดนี้ไม่ใช้ username/password ระบบ UAT จึงใช้ **HTTPS ร่วมกับการจำกัด IP ต้นทางธนาคาร** ทั้งที่ ingress และในแอป พร้อมจำกัด proxy ที่เชื่อถือได้เฉพาะตัวที่ใช้งานจริง

Header หลักที่รองรับคือ `Content-Type: application/json; charset=UTF-8`, `Service-Name: credit-notification` และ `Request-Datetime` การใส่ header เหล่านี้อย่างเดียวไม่ใช่หลักฐานยืนยันตัวตน เพราะผู้เรียกทั่วไปก็ใส่ได้

การเปลี่ยน IP ของผู้ใช้เว็บไซต์ไม่ควรทำให้ซื้อสินค้าไม่ได้ กฎจำกัด IP ของธนาคารใช้กับ callback ของธนาคาร ไม่ใช่ผูกลูกค้าทุกคนไว้กับ IP เครื่องผู้พัฒนา

### ทำไมคอนโซลใช้ SSH

คอนโซล TEST เปิดเฉพาะ loopback ของ API และต้องเข้าผ่าน SSH tunnel ที่ใช้สิทธิ์ SSH เดิม ไม่มีการเปิดคอนโซลไว้บน URL สาธารณะ ผู้ที่มีสิทธิ์ SSH ระดับนี้สามารถสั่งงานทดสอบได้ จึงต้องดูแลสิทธิ์ SSH เหมือนสิทธิ์ผู้ดูแลระบบ

คำขอเปลี่ยนข้อมูลต้องมี header เฉพาะของคอนโซลและมาจาก origin เดียวกัน ระบบตรวจ socket ต้นทางก่อนอ่าน forwarded headers เพื่อไม่ให้ผู้ใช้อินเทอร์เน็ตปลอม X-Forwarded-For เป็น localhost แล้วเข้าได้

## 4. Feature Ref1=TEST ที่เพิ่ม

### การแยกเส้นทาง

หลังตรวจว่า callback มาจากธนาคารแล้ว API จะตรวจ Ref1 ถ้าเท่ากับ `TEST` แบบตรงตัว จะส่งเข้าชุดข้อมูลทดสอบ นอกจากนี้ยังจดจำ QRId ที่สร้างในคอนโซล แม้ภายหลังได้รับ Ref1 ผิด รายการนั้นก็ยังถูกเก็บเป็นเหตุการณ์ทดสอบ

callback ที่ Ref1 ปกติยังใช้ระบบออเดอร์เดิม การจับคู่ QR หรือ InstructionId ของออเดอร์ซื้อสินค้าจากคอนโซล TEST จะถูกปฏิเสธ

| ข้อมูลใหม่ในฐานข้อมูล | ใช้ทำอะไร |
|---|---|
| BankTestCases | เก็บ QR อ้างอิง ยอด และสถานะของแต่ละชุดทดสอบ |
| BankTestEvents | เก็บประวัติสร้าง QR, noti, Verify, Void และ Enquiry Void |
| BankTestReceipts | จำ InstructionId และผล ACK เพื่อรับ noti ซ้ำอย่างถูกต้อง |
| BankTestOperations | บันทึกคำขอออกไปธนาคาร พร้อมรหัสป้องกันส่งซ้ำและผลล่าสุด |

ตารางเหล่านี้ไม่มี foreign key ไปยังออเดอร์ สต็อก สิทธิ์สินค้า หรือใบเสร็จ การรับ noti TEST จึงไม่เพิ่มยอดขายหรือส่งสินค้า

### สองกรณีที่คอนโซลรับได้

**QR ที่สร้างจากคอนโซล:** มีวันสร้างและข้อมูล QR ครบ ถ้า noti หรือผล Verify ตรงกัน จะเป็น Paid และมีสิทธิ์เข้าสู่ขั้นตอนตรวจเงื่อนไข Void

**noti TEST จาก QR ภายนอก:** บันทึกเป็น Observed แสดง log และสั่ง Verify ได้ แต่ไม่ให้ Void จากคอนโซล เพราะระบบไม่มีหลักฐานเวลาออก QR เดิม ให้สร้าง QR ผ่านคอนโซลก่อนถ้าต้องการทดสอบครบวงจร

### ค่าที่เปิดใช้ใน UAT

Ref1=`TEST` | ค่าเริ่มต้น QR=1 บาท | วงเงินสูงสุด=100 บาทต่อชุด | Verify สูงสุด=10 ครั้งต่อชุด | Enquiry Void สูงสุด=3 ครั้งต่อชุด

Verify ต้องรออย่างน้อย 60 วินาทีหลังสร้างชุด และเว้นระยะคำขอธนาคารอย่างน้อย 30 วินาที มีงบจำนวนคำขออ่านต่อ merchant ร่วมกับระบบหลักด้วย การ refresh หน้าเว็บอัตโนมัติอ่านฐานข้อมูลของเรา ไม่ได้ยิง Verify อัตโนมัติ

## 5. วิธีเปิดและใช้งานคอนโซล

เปิด PowerShell ที่โฟลเดอร์ Unity project แล้วรัน:

```powershell
.\Infrastructure\TTB\uat\open-bank-test-console.ps1
```

เปิด URL นี้ในเบราว์เซอร์ โดยเปิดหน้าต่าง PowerShell ค้างไว้:

```text
http://127.0.0.1:18765/internal/bank-test-console/
```

ถ้า port18765 ถูกใช้อยู่ ให้เพิ่ม `-Port 18766` และเปิด URL ด้วย port ใหม่ กด Ctrl+C เมื่อต้องการปิด tunnel ถ้า API rollout แล้ว tunnel หลุด ให้เปิดสคริปต์ใหม่

### ทดลอง Notification และ Verify กับคุณ Bird

1. กรอกยอด เช่น 1.00 แล้วกดสร้าง QR ระบบกำหนด Ref1=TEST ให้เอง
2. ตรวจชื่อบริษัท ยอด Ref2 และ QRId จากนั้นดาวน์โหลด QR เพื่อส่งให้คุณ Bird สแกนในวงทดสอบธนาคาร
3. ใช้ QR ภายในเวลาหมดอายุที่แสดง หากหมดอายุแล้วให้สร้างใบใหม่
4. ดูตารางเหตุการณ์ ถ้ารับ noti แล้วจะเห็น Notification พร้อมรหัส ACK และสถานะ Paid เมื่อข้อมูลตรงกัน
5. เมื่อครบเวลารอ สามารถกด Verify เพื่อขอผลจาก TTB เพิ่มได้ หน้าจอแสดง HTTP status รหัสธุรกิจ และ Request UID ของคำขอนั้น
6. กดรายการในตารางเพื่อดู JSON ที่คัดเฉพาะข้อมูลจำเป็น หรือกดบันทึก log JSON เพื่อส่งต่อประกอบการตรวจปัญหา

### ทดลอง Void

ใช้รายการที่สร้างในคอนโซลและชำระสำเร็จแล้วเท่านั้น กด Void ตรวจยอด QRId และ InstructionId ในหน้าต่างยืนยัน แล้วติ๊กยืนยันรายการ TEST ก่อนกดส่ง ระบบไม่สั่ง Void เพียงเพราะได้รับ noti

คอนโซลใช้ข้อจำกัดแบบระมัดระวัง: วันเดียวกันตามเวลาไทย ต้องมีเวลาออก QR และเวลาที่สังเกตเห็นเงินเข้าซึ่งอยู่ในขอบเขตเดียวกัน และเผื่อเวลาอย่างน้อย 30 วินาทีก่อน 22:56 น. ไม่รองรับรายการ cross-border ใน feature นี้ ข้อจำกัดนี้เป็นนโยบายของคอนโซล ไม่ใช่การยืนยันสิทธิ์ Void ทุกกรณีของธนาคาร

ถ้าได้ Unknown หรือ timeout อย่าสร้างคำขอ Void ซ้ำ ให้กด **สอบถามผล Void** ซึ่งใช้ TransactionId เดิม ระบบบันทึกเจตนาส่งก่อนติดต่อธนาคาร เพื่อไม่ส่งซ้ำแม้หน้าต่างปิดหรือโปรแกรมหยุดระหว่างทาง

## 6. ดู log ด้วยตัวเอง

คำสั่งต่อไปนี้รันจาก PowerShell ในโฟลเดอร์ Unity project ใช้ SSH alias `ntserver02` ที่ตั้งไว้แล้ว การดู log ไม่ต้องเปิด tunnel หน้าเว็บก่อน

### ประวัติทดสอบที่เก็บในฐานข้อมูล


### เฝ้าดูเหตุการณ์ TEST ที่เพิ่งเกิดขึ้น

## 7. อ่านผลและแก้ปัญหาเบื้องต้น

รหัสเดียวกันอาจมีความหมายต่างกันในแต่ละ API ให้ดูชื่อ operation ประกอบทุกครั้ง

| เหตุการณ์/ผล | ควรเข้าใจอย่างไรและทำอะไรต่อ |
|---|---|
| Notification ACK0000 | ระบบรับข้อมูลและบันทึกผลแล้ว สำหรับ TEST ให้ดูสถานะและ Outcome ในคอนโซลด้วย |
| Notification ACK0004 | InstructionId เดิมส่งมาอีก ระบบไม่สร้างผลทางการเงินซ้ำ |
| Notification ACK0001 | รูปแบบ/header ไม่ถูกต้อง หรือ InstructionId ขัดแย้ง ให้เทียบ log กับผู้ส่ง |
| ACK0003 /0005 /0006 /0007 | ตรวจ BillerNo /ยอด /Ref1 /Ref2 ตามลำดับ |
| Verify HTTP200 +0002 | ติดต่อสำเร็จ แต่ไม่พบรายการชำระ ยังถือว่าจ่ายสำเร็จไม่ได้ |
| Verify Found | พบหลักฐานที่ parser ยอมรับ ต้องจับคู่ยอดและอ้างอิงถูกต้องจึงเปลี่ยนสถานะ |
| HTTP401 จาก TTB | การยืนยันตัวตน API ไม่ผ่าน ตรวจ issuer, key ที่ธนาคารลงทะเบียน, อายุ JWT และเวลาของเครื่อง |
| HTTP403 ที่ callback | ต้นทางไม่อยู่ในรายการธนาคาร หรือความเชื่อถือ proxy ไม่ตรง ต้องตรวจ network path |
| HTTP429 ในคอนโซล | ถี่เกินช่วงพักหรืองบจำนวนครั้ง รอตามเงื่อนไข ไม่กดซ้ำต่อเนื่อง |
| VoidUnknown / Unknown | ยังพิสูจน์ผล Void ไม่ได้ ใช้ Enquiry Void และประสานธนาคารด้วย TransactionId/Request UID เดิม |
| Review | พบข้อมูลขัดแย้ง ต้องตรวจรายละเอียดก่อนดำเนินการต่อ |

### จ่ายแล้วแต่หน้าเว็บยังไม่เปลี่ยน

เริ่มจากตรวจเลขออเดอร์ให้ตรงกับ QR ที่จ่าย อ่าน `-View Order` ว่ามี payment และ callback หรือไม่ ถ้าเงินเป็น Paid แต่ fulfillment ยังไม่ Delivered ให้ดู worker ถ้าเอกสารยังไม่ Ready ให้ดู receipt worker

ถ้าไม่มี callback ให้เทียบเวลา QRId/Ref1 กับธนาคารและตรวจ ingress/ต้นทาง ไม่แก้ฐานข้อมูลให้ Paid จากภาพสลิปอย่างเดียว ใช้ Verify ผ่านช่องทางที่มีสิทธิ์เพื่อตรวจหลักฐานเพิ่มเติม

### QR TEST สแกนแล้วแต่ไม่เห็นของใน “สินค้าของฉัน”

นี่เป็นพฤติกรรมที่ตั้งใจไว้ งาน TEST ไม่ผูกกับผู้ซื้อและไม่ส่งสินค้า ถ้าต้องการทดสอบการซื้อและการส่งสินค้าครบวงจร ให้ซื้อผ่านหน้า UAT ตามปกติ ซึ่งจะใช้ Ref1 เป็นเลขออเดอร์แทน TEST

### ความคงทนและการป้องกันส่งซ้ำ

noti ใช้ transaction ของ PostgreSQL กับ lock ตาม InstructionId/QRId และ unique constraint เมื่อข้อมูล commit แล้วจึงตอบ ACK การส่งคำขอออกใช้ OperationId แบบ UUID ที่คงเดิมสำหรับคำขอเดิม และบันทึก send fence ก่อน HTTP call

Void ส่งได้หนึ่งครั้งต่อชุด แม้เคยได้ผลปฏิเสธก็ให้สร้างการทดสอบใหม่ หากไม่ทราบผลให้ใช้ Enquiry Void จำนวนครั้งและ cooldown ตรวจที่ backend ด้วย ไม่อาศัยเพียงการปิดปุ่มบนหน้าจอ

### Log และข้อมูลส่วนบุคคล

event เก็บ raw payload ในฐานข้อมูลภายในเพื่อ audit ส่วนคอนโซลและไฟล์ export คัดเฉพาะ field ที่จำเป็น ไม่แสดง PayerName/PayerAccount และไม่เก็บ Authorization header ใน event Log จอภาพเป็นสรุป operation, ref, QRId, ยอด และรหัสผล ผู้ดูแลฐานข้อมูลยังมีสิทธิ์เข้าถึง raw หลักฐานได้ จึงควรจัดสิทธิ์และนโยบายเก็บข้อมูลตามงานจริง

Release ใช้ reader contract4 เพื่อห้าม deploy กลับไปยัง binary เก่าที่ไม่รู้จักการแยก TEST สำรองข้อมูลชุดใหม่ต้องระบุ contract4 ด้วย การแก้ไขครั้งต่อไปควรเป็น forward release ที่รองรับข้อมูลเดิม

## 9. ผลตรวจรับและสิ่งที่ต้องดูแลต่อ

## 10. ตรวจรับกับธนาคารและดูแลต่อ

### การตรวจรับร่วมกับธนาคารที่ยังต้องใช้การสแกนจริง

หลังติดตั้ง ให้สร้าง QR TEST ใหม่จากคอนโซล ส่งให้คุณ Bird สแกนในวง UAT ดู noti และ Verify จากนั้นนัดทดสอบ Void กับรายการ TEST นั้น การทดสอบโปรแกรมผ่านไม่แทนการยืนยันผลของธนาคารทุก feature ใหม่

### ดูแลระบบระยะต่อไป

- ติดตามวันหมดอายุ cert และกระบวนการเปลี่ยน cert ของ TTB รวมถึง key ที่แต่ละฝ่ายลงทะเบียน
- ถ้า IP ของธนาคารหรือ ingress เปลี่ยน ต้องตรวจและปรับ allowlist/trusted proxy ตามหลักฐานจริง ไม่เปิดทั้งอินเทอร์เน็ต
- ตรวจ backup, พื้นที่ฐานข้อมูล/ไฟล์ และการกู้คืนด้วยรุ่นโปรแกรมที่เข้ากันได้ ข้อมูล TEST เก็บถาวรจนมีนโยบายล้างที่อนุมัติแยก
- SFTP/report, Production key/callback และการเปิดใช้งานจริงต้องตรวจรับเป็นขั้นตอนของตนเอง รายงานนี้ไม่ได้ถือว่า Production พร้อมใช้งานแล้ว
- ถ้าต้องการให้ธนาคารเปิดคอนโซลเองจากภายนอก ต้องออกแบบบัญชีและสิทธิ์เฉพาะเพิ่มเติม รุ่นนี้สำหรับผู้ดูแลที่มี SSH เท่านั้น ไม่ส่งสิทธิ์ root SSH ให้ธนาคาร

**วิธีเริ่มใช้งานเร็วที่สุด:** เปิดคอนโซลด้วยสคริปต์ในหัวข้อ5 สร้าง QR1บาทให้ Ref1=TEST แล้วดูประวัติในตาราง หรือใช้คำสั่ง `get-uat-log.ps1 -View Tests` ในหัวข้อ6
